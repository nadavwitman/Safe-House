# services

The app's entire backend/device boundary — every HTTP call, all local persistence, and the shared in-memory session state every screen reads. Nothing in [screens/](../screens/admin/README.md) talks to `http` or `SharedPreferences` directly; it goes through here.

## Core plumbing

- **[api_client.dart](api_client.dart)** — `ApiClient`, the single HTTP layer. `get`/`post`/`delete` attach the JWT from `AuthState.instance.accessToken`; `postPublic` skips auth for sign-in/sign-up. On a 401 it transparently calls `_tryRefresh()` (POSTs the refresh token, updates `AuthState`) and retries the request exactly once (`isRetry` guards against a refresh loop) — so a screen only ever sees an `ApiException` if re-authentication itself failed, not on an ordinary expired access token. `ApiException` carries the HTTP status and the server's `error` message; a `SocketException` becomes a fixed "no internet" `ApiException(0, …)` instead, so every caller can catch one exception type regardless of cause.
- **[auth_state.dart](auth_state.dart)** — `AuthState.instance`, the app-wide singleton holding the session: tokens, `AppUser` (with its `houses` list), the active house id, and four `ValueNotifier`s (`vacationMode`, `weeklyReportAt`, `unreadAlerts`, `currentAlertId`) that let unrelated tabs react to state none of them individually own — see [screens/customer](../screens/customer/README.md) for how the dashboard poll, the Alerts tab, and the Profile tab each publish or consume one of these without a direct reference to each other. Persists tokens, the active house id, and a per-house vacation flag to `SharedPreferences` (`_vacationKey` is namespaced per house id, not shared, precisely so switching houses can't carry the previous resident's pause state across). `clear()` is the sign-out path: it wipes every persisted key, including sweeping every `vacation_mode_*` key rather than just the active one, and delegates to `WeeklyReportCache.clearAll()` / `AlertAckStore.clearAll()` so a shared device never leaks one account's data to the next.

## Backend API wrappers (thin — one method per endpoint)

- **[auth_service.dart](auth_service.dart)** — `AuthService.signIn`/`signUp`/`signOut`/`changePassword`/`changeUsername`, all through `/api/auth/*`. Sign-in's response has house *ids* only; `AuthState.currentUser.houses` stays empty until `UserService.getProfile()` fills in full house objects. `signOut` unregisters the FCM token before calling the server, and clears local state (`AuthState.clear()`) even if the server call throws — a network failure must not leave a signed-out-looking UI still holding a live session.
- **[user_service.dart](user_service.dart)** — `UserService.getProfile()` (sign-in/launch: refreshes the account *and* re-registers the push token) vs. `refresh()` (routine Profile-tab freshening: account only, no redundant FCM POST) — two entry points into the same `/api/user/me` call, split by whether push registration needs touching. `joinHouse()` refreshes the JWT itself after joining, since the new `house_id` has to be embedded in the token's claims before any `@house_member_required` backend route (see [Backend_Server/app/auth](../../../../Backend_Server/app/auth/README.md)) will accept it.
- **[admin_service.dart](admin_service.dart)** — every `/api/admin/*` call used by [screens/admin](../screens/admin/README.md): list/get/create/delete house, regenerate invite code, rotate device token, remove a user, set the sensor mask. No local state of its own — purely a typed pass-through.
- **[house_service.dart](house_service.dart)** — `HouseService.getStatus(houseId)`, the one call behind the dashboard's 30-second poll (`/api/house/<id>/status`). Documented as a single Firestore read server-side, which is why polling it that often is fine — see [Backend_Server/app/api](../../../../Backend_Server/app/api/README.md).
- **[insights_service.dart](insights_service.dart)** — `getWeeklyReport` and `getAlerts` (`/api/insights/*`), both **read-only by design**: there is deliberately no endpoint here that could make a report exist or spend a Gemini call — reports are written only by the backend's weekly job and its catch-up path (see [Backend_Server/app/weekly_summary](../../../../Backend_Server/app/weekly_summary/README.md)).
- **[config_service.dart](config_service.dart)** — vacation-mode writes (`setMode`, `setSchedule`, `clearSchedule`), all returning a `VacationResult` (`isVacation`, `scheduleCleared`). The result is parsed from what the *server* says happened rather than re-derived from the request, because these calls have side effects wider than their name suggests (e.g. turning monitoring back on server-side deletes an in-progress trip) — duplicating that arithmetic client-side would drift from the server's copy.
- **[notification_service.dart](notification_service.dart)** — wraps `firebase_messaging`: requests permission, registers/unregisters the device's FCM token against `/api/user/fcm-token`, and listens for token refresh. Everything is wrapped in silent `catch (_) {}` — a push-registration failure must never block sign-in or crash startup, since push is an enhancement, not a requirement for the app to function. No-ops entirely on web (`kIsWeb`), since FCM there needs a service worker/VAPID setup the project doesn't have.

## Local-only persistence (device state that never reaches the server)

- **[alert_ack_store.dart](alert_ack_store.dart)** — `AlertAckStore`, per-house, per-device sets of acknowledged alert ids in `SharedPreferences`, keyed by the alerts endpoint's Firestore document id (nothing else about an alert is unique — two sensors can fault in the same second). Acknowledgement is a deliberate device-local fact ("I have read this"), never sent to the server, mirroring the dashboard banner's behavior — see [screens/customer](../screens/customer/README.md). `prune()` drops ids that have aged out of the server's 7-day window, but only against a *complete* fetch (a partial/failed one would wrongly forget still-visible acknowledgements), and always spares whichever id is passed as `keep` — the alert currently in effect, which can be older than 7 days but is still the one showing on the dashboard.
- **[weekly_report_cache.dart](weekly_report_cache.dart)** — `WeeklyReportCache`, one cached report JSON blob per house. This is the mechanism that makes the Summary tab's caching scheme (described in `screens/customer/README.md`) actually work: the tab compares this cache's `generated_at` against the live poll's `weekly_report_at` and only re-fetches on a mismatch. An unparseable cached entry (e.g. after a shape change across app versions) is treated as no cache rather than surfaced as an error.

Both stores expose a `clearAll()` swept by `AuthState.clear()` on sign-out.
