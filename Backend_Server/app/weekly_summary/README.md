# app/weekly_summary

Generates the AI-written weekly wellness report shown in the app's Summary tab. Pulls a week of raw sensor readings (vacation-flagged readings excluded — see `get_weekly_sensor_data()` in [database/repositories](../../database/repositories/README.md)), turns them into structured per-day metrics, compares them against the resident's personal EMA baseline, and asks Gemini to turn that into a warm, non-alarming narrative. Triggered from two places that both funnel through the same `generate_and_store()`: the Sunday scheduler (`app.__init__`'s `_setup_scheduler`, duplicated in [entrypoints/run.py](../../entrypoints/README.md) for local dev) and the lazy catch-up in [catchup.py](catchup.py). Both skip a house outright while it's currently on vacation, rather than generating a report off a filtered-down week. There is no on-demand "generate" route — see [app/api](../api/README.md)'s note on `insights_routes.py`.

## Pipeline

1. **[aggregator.py](aggregator.py)** `aggregate_weekly_metrics()` — turns a week of raw `(sensor_vector, current_location, time)` docs into one dict per day. Localizes timestamps to `LOCAL_TZ`, computes a data-coverage fraction per day (and per overnight sleep window) and nulls out a day's metrics entirely if coverage falls below `MIN_COVERAGE_FRACTION` — a mostly-missing day must never be miscounted as inactivity. The actual per-category math is delegated to **[metrics/](metrics/README.md)**.
2. **[baseline.py](baseline.py)** — maintains each house's personal norm as an exponential moving average (`ALPHA = 0.05`, i.e. each week nudges the baseline 5% toward itself). `compute_weekly_averages_for_baseline()` extracts this week's averages (with medications kept per-weekday since meds timing is inherently daily, not a flat weekly number); `build_new_baseline()` seeds or updates the stored baseline; `compute_deltas()` returns `current - baseline` for every metric, `None` on the very first week (no baseline yet).
3. **[report_generator.py](report_generator.py)** — the orchestrator:
   - `run_insights_pipeline()` — loads the house's sensor mask and stored baseline, calls the aggregator and baseline functions above, requires at least 5 distinct days of data (else returns `(None, None)`), and only *advances* the stored baseline when `advance_baseline=True` — the scheduled weekly run may, but the catch-up path deliberately does not (see below).
   - `format_compact_prompt()` — renders the metrics/averages/deltas into a compact plain-text block for the LLM prompt, explicitly flagging any low-coverage day as "insufficient sensor data" so the model doesn't read a device outage as poor sleep or a skipped meal.
   - `generate_weekly_report()` — calls Gemini (`gemini-2.5-flash`) with a fixed JSON-structured prompt (`summary`, per-category `insights`, `recommendations`), retrying with exponential backoff on rate-limit/overload errors.
   - `generate_and_store()` — the single entrypoint every caller uses: fetches the week's raw docs, runs the pipeline, wraps the result with `period`/`generated_at`, and persists it. Defines the stored report's shape once so the scheduler and catch-up can never drift apart on it.
4. **[catchup.py](catchup.py)** `maybe_catch_up(house_id, weekly_report_at, catchup_attempted_at, is_vacation=False)` — lazy repair for houses whose Sunday report never landed (Gemini failure, server down past the misfire window). Returns immediately if `is_vacation` is true (passed in for free from the same house-doc read the dashboard poll already made — vacation readings are filtered out server-side anyway, so regenerating now would just burn a Gemini call on a thin or empty week and back off the real regeneration once the resident is back). Otherwise piggybacks on the dashboard poll that already reads the house doc: if the report is stale (`STALE_AFTER` = 8 days) or missing, and no attempt was made in the last `RETRY_AFTER` (24h), it transactionally claims the house (so concurrent family-member polls produce one regeneration, not several) and regenerates in a background thread. Deliberately calls `generate_and_store(..., advance_baseline=False)` — the EMA assumes exactly one update per week, and a catch-up firing at an arbitrary moment must never double-count or skew it.

## Files

- **[constants.py](constants.py)** — `ZONE_NAMES`, `MAX_ATTRIBUTABLE_GAP_MINUTES` (caps how much duration a single reading gap can contribute, so a connectivity outage can't be miscounted as presence), `LOCAL_TZ`, `MIN_COVERAGE_FRACTION`.
- **[aggregator.py](aggregator.py)** — per-day/per-week metric aggregation and the coverage gate; see above.
- **[baseline.py](baseline.py)** — EMA baseline maintenance and delta computation; see above.
- **[report_generator.py](report_generator.py)** — prompt formatting, Gemini call, and the pipeline/storage orchestrator; see above.
- **[catchup.py](catchup.py)** — lazy, transactional regeneration for overdue reports, skipped outright while the house is on vacation; see above.
- **[metrics/](metrics/README.md)** — the six per-category daily metric computations (sleep, mobility, nutrition, cognitive/duration, meds, socialization) called by `aggregator.py`. See its own README for details.
